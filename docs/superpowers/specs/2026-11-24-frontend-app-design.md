# ออกแบบ: แอป fishpump สำหรับเจ้าของบ่อและเจ้าของกิจการ

วันที่: 2026-11-24 · สถานะ: **ร่าง รอผู้ใช้อนุมัติ** · ขนาดงาน: โปรเจกต์

หน้าตาที่อนุมัติแล้วอยู่ในกระดาน Design "fishpump ทุกหน้าจอ" (https://claude.ai/artifact/SoikqTc7rZKFhXPMNvKwKX) มี 36 จอใน 6 หน้า เอกสารนี้อ้างจอด้วยรหัสบนกระดาน เช่น ข1 หรือ จ8 ไฟล์ต้นฉบับของกระดานอยู่นอก repo ผู้สร้างเปิดดูได้จากลิงก์เท่านั้น

## 1. เจตนาและเหตุผล

- **ผู้ใช้หลักคือเจ้าของบ่อปลาคาร์ป** มีตั้งแต่วัยทำงานถึงวัยเกษียณ ใช้มือถือดูบ่อและสั่งปั๊มตอนไม่อยู่บ้าน
- **ผู้ใช้รองคือเจ้าของกิจการ (ร้านติดตั้ง) และช่างของร้าน** ใช้คอมเป็นหลัก ดูแลบ่อของลูกค้าทุกราย
- **ความปลอดภัยของปลามาก่อนทุกอย่าง:** เรื่องอันตรายต้องเห็นทันที และแก้กลับเป็นปกติได้ง่าย ค่าที่ตั้งผิดแล้วทำให้ปลาตายหรือปั๊มไหม้ ลูกค้าต้องแก้ไม่ได้
- **ผู้ใช้ (นักพัฒนา) ต้องดูแลแอปนี้หลายปี:** จึงต้องการของที่ดูแลง่าย ไม่มีเซิร์ฟเวอร์ของเราเองเพิ่ม และใช้ ThingsBoard CE ต่อไปเท่านั้น
- ตอนนี้ลูกค้าดูบอร์ดผ่าน dashboard ทดสอบของ ThingsBoard ซึ่งใช้ยากบนมือถือ และไม่เหมาะกับผู้สูงวัย

## 2. สภาพปัจจุบัน (ตรวจแล้ว 2026-11-24)

- **`frontend-app/`:** ใน git มีแค่ `.gitkeep` บนเครื่องผู้ใช้ยังมี `node_modules/` และ `dist/` เก่าที่ gitignore ไว้ (มาจาก AI Studio) ไม่ใช้ต่อ
- **ThingsBoard:** รุ่น CE 4.3.1 ตอนนี้ตั้งบนเครื่อง copter ด้วยมือ
  - `thingsboard/tb_setup.py` สร้าง rule chain `fishpump`, device profile `fishpump` (ลงทะเบียนเองด้วย provision key) customer ทดสอบ และ dashboard ทดสอบ รันซ้ำได้
  - `thingsboard/rule_chains/fishpump.json` คือ rule chain ที่ใช้อยู่
- **สัญญากับบอร์ดอยู่ใน `docs/firmware/device-api.md`:**
  - RPC 38 method (ข้อ 9)
  - client attribute 6 key (`cfg_pump`, `cfg_cooling`, `cfg_protection`, `hardware_map`, `wifi`, `tb_link`) ในข้อ 11.1
  - status telemetry ในข้อ 11.2
  - telemetry ค่าเซนเซอร์ทุก 30 วินาที (ดู `docs/backlog/thingsboard-data-and-deploy.md` ข้อ 1)
- **บอร์ดกันเองอยู่แล้วบางส่วน:**
  - `hardware.map.set` และ `wifi.disconnect` สั่งได้จากบอร์ดเท่านั้น (LOCAL_ONLY)
  - ขั้วรีเลย์แก้จาก ThingsBoard ไม่ได้
  - `cooling.config.set` บังคับ `min_off_sec` ≥ 120
  - `protection.set` ตรวจช่วงค่าใน `dry_run_config_validate` (`firmware/components/dry_run_logic/`): `prime_sec` 1..600, `dry_trip_sec` 3..120, `retry_wait_min` 1..240, `max_retries` 0..5 ช่วงนี้ยังกว้าง ปั๊มเดินแห้งได้ถึง (600+120) วินาที × 6 รอบ หรือราว 72 นาที
  - ถ้าค่าที่เก็บในบอร์ดไม่ผ่านการตรวจตอนเปิดเครื่อง บอร์ดจะใช้ค่าเริ่มต้นแทน ซึ่งค่าเริ่มต้นคือ **ปิดการกันปั๊มเดินแห้ง** (`nvs_store_load_dry_run`)
- **การเปลี่ยน Wi‑Fi จากระยะไกล:** ย้อนกลับเองถ้าต่อไม่ติด ส่วน OTA ย้อนกลับรุ่นเดิมเองถ้ารุ่นใหม่ต่อเซิร์ฟเวอร์ไม่ได้ใน 5 นาที
- **ข้อจำกัด CE ที่ตรวจจากซอร์ส ThingsBoard master:** RPC ที่ส่งผ่าน REST API เข้า rule engine เป็นข้อความ `RPC_CALL_FROM_SERVER_TO_DEVICE` แต่ metadata มีแค่ `requestUUID`, `originServiceId`, `expirationTime`, `oneway`, `persistent`, `deviceName`, `deviceType` **ไม่มีข้อมูลผู้สั่ง** ดังนั้น rule chain จึงแยกไม่ได้ว่าใครเป็นคนสั่ง

## 3. เป้าหมาย / ไม่ใช่เป้าหมาย / ล้มเหลวแม้ทำงานได้

**เป้าหมาย**
1. แอปเว็บใช้บนมือถือได้ทั้งแบบเปิดใน browser และแบบติดตั้งลงหน้าจอ (PWA) โดยมีทุกจอตามกระดาน
2. เจ้าของบ่อเห็นสถานะบ่อจริงจาก ThingsBoard ได้ทันที และสั่งเปิดหรือหยุดปั๊มได้พร้อมรู้ผลจริงจากบอร์ด
3. เจ้าของกิจการและช่างดูแลทุกบ่อได้ ได้แก่ ดูภาพรวม เพิ่มลูกค้า ผูกบอร์ด อัปเดตบอร์ด และแก้ค่าที่อันตราย
4. ค่าที่อันตรายเปลี่ยนได้เฉพาะคนของร้าน และบอร์ดไม่รับค่าที่เกินขีดปลอดภัย (ข้อ 6)
5. ใช้กับ ThingsBoard CE ได้โดยไม่มีเซิร์ฟเวอร์ของเราเอง

**ไม่ใช่เป้าหมายรอบนี้**
- แอป native บน App Store หรือ Play Store
- การแจ้งเตือนเด้งบนมือถือ (push) เพราะต้องมีเซิร์ฟเวอร์ส่ง ตามแผนเดิมให้ ThingsBoard ส่ง LINE หรือ email ในโปรเจกต์ deploy
- การ deploy บน VPS, TLS และนโยบายเก็บข้อมูล ซึ่งอยู่ใน `docs/backlog/thingsboard-data-and-deploy.md`
- หลายภาษา: รอบนี้มีแต่ภาษาไทย
- งานเฟิร์มแวร์อยู่ในข้อ 13 ทำแยก branch แต่ต้องเสร็จก่อนให้ลูกค้าใช้แอป

**ล้มเหลวแม้ทำงานได้**
- แอปบอกว่าปั๊มทำงาน แต่บอร์ดยังไม่ได้ยืนยัน
- ค่าเก่าดูเหมือนค่าสด
- ผู้สูงวัยอ่านค่าหรือหาปุ่มแก้เรื่องอันตรายไม่เจอ
- ลูกค้าที่รู้จัก REST API ของ ThingsBoard ตั้งค่ากันปั๊มเดินแห้งให้อันตรายได้

## 4. ข้อจำกัด

- **ThingsBoard ต้องเป็น CE เท่านั้น** (ผู้ใช้สั่งเมื่อ 2026-11-24) จึงไม่มี role ละเอียด ไม่มี scheduler และไม่มี customer ซ้อนกัน
- **ไม่มีเซิร์ฟเวอร์ของเราเอง:** แอปเป็นไฟล์เว็บนิ่ง คุยกับ REST และ WebSocket ของ ThingsBoard โดยตรง
- **ห้ามแก้หน้าเข้าสู่ระบบตามธีม:** หน้านี้มีหน้าตาเดียวตามกระดาน คือภาพบ่อมืด ปุ่มทอง และแผ่นกระจก
- **ใช้กับผู้สูงวัยได้:**
  - ตัวหนังสือ 17px ขึ้นไป
  - จุดแตะ 48px ขึ้นไป ส่วนปุ่มหลักสูง 56–58px
  - ตัวหนังสือกับพื้นตัดกันอย่างน้อย 4.5:1
  - ทุกสถานะบอกด้วยไอคอน คำ และสีพร้อมกัน
  - ทุกการขยับหยุดเมื่อเครื่องตั้ง "ลดการเคลื่อนไหว"
- **ข้อความในแอปต้องตรงกับความจริงของระบบ:** เช่น ค่าเซนเซอร์มาทุก 30 วินาที ไม่ใช่ 2 วินาที

## 6. ผู้ใช้ สิทธิ์ และการกันค่าที่อันตราย (บน CE)

### 6.1 บัญชี

| คน | บัญชีใน ThingsBoard | เห็นอะไร |
|---|---|---|
| เจ้าของร้าน | Tenant Administrator | ทุกบ่อ ทุกเมนู รวมจอ จ1–จ8 |
| ช่าง (คนละบัญชีต่อคน) | Tenant Administrator | เหมือนเจ้าของร้าน แต่แอปซ่อนเมนูตั้งค่าร้านและบัญชีช่าง |
| ลูกค้า | Customer User ของ Customer รายนั้น โดยบ่อของเขาถูกมอบ (assign) ให้ Customer นั้น | เฉพาะบ่อของตัวเอง จอ ก, ข, ค, ง |

- แอปรู้ว่าใครเป็นใครจาก `authority` ของผู้ใช้ (`TENANT_ADMIN` หรือ `CUSTOMER_USER`)
- แอปแยกเจ้าของร้านกับช่างด้วยค่าใน `additionalInfo` ของผู้ใช้ เช่น `fishpump_role: "owner" | "technician"`
- **ข้อจำกัดของ CE:** ช่างทุกคนมีสิทธิ์ใน ThingsBoard เท่าเจ้าของร้าน การซ่อนเมนูจึงกันแค่กดผิด ไม่ได้กันคนตั้งใจ ซึ่งยอมรับได้เพราะช่างเป็นพนักงานของร้าน ส่วน audit log ของ ThingsBoard บันทึกไว้ว่าใครทำอะไร
- **ตัด "ลูกค้าดูอย่างเดียว" ออก:** CE กันทีละคนไม่ได้ ลูกค้าทุกคนใน Customer เดียวกันสั่งงานได้เท่ากัน

### 6.3 วิธีกัน 3 ชั้น

1. **ทางของร้าน:** แอปไม่ส่งค่าที่อันตรายเป็น RPC ตรงไปที่บอร์ด
   - ร้านมี asset ต่อบอร์ดหนึ่งตัว เป็นของ tenant และไม่มอบให้ลูกค้า ลูกค้าจึงเข้าไม่ถึง
   - แอปของช่างเขียนคำขอลง server attribute ของ asset นั้น เช่น `apply_request = {method, params, request_id}`
   - rule chain รับเหตุการณ์ attribute เปลี่ยนของ asset แล้วเปลี่ยนผู้ส่งเป็นบอร์ดที่ผูกไว้ ส่ง RPC ไปที่บอร์ด แล้วเขียนผลกลับลง `apply_result` ของ asset
   - แอปรอผลจาก `apply_result`
2. **ทางตรงถูกทิ้ง:** ในขา `RPC_CALL_FROM_SERVER_TO_DEVICE` ของ rule chain `fishpump` เพิ่ม node ทิ้งคำสั่งที่ method อยู่ในแถว "ค่าที่อันตราย" ของข้อ 6.2 (รวม `cooling.mode.set` ที่ mode เป็น test) ไม่ว่าใครส่ง คนของร้านก็ต้องใช้ทางในข้อ 1
   - **ข้อยกเว้นสำหรับบอร์ดทดสอบ (ผมตัดสินเอง):** ถ้า asset ของร้านที่ผูกกับบอร์ดนั้นมี server attribute `bench_allow_direct = true` จะไม่ทิ้ง ทำให้ `parity_test.py` และ dashboard ทดสอบยังใช้ได้กับบอร์ดบนโต๊ะ ค่าเริ่มต้นคือ false และลูกค้าแก้ไม่ได้เพราะเข้าไม่ถึง asset
   - ลูกค้าย้ายจาก dashboard ทดสอบมาใช้แอปนี้ ส่วน dashboard ทดสอบเหลือไว้ให้คนของร้าน
3. **บอร์ดกันเอง (ด่านสุดท้าย):** เฟิร์มแวร์ไม่รับค่าที่เกินขีดปลอดภัย ไม่ว่าค่านั้นมาจาก ThingsBoard หรือหน้าเว็บของบอร์ด งานแคบขีดอยู่ในข้อ 13

**ต้องทดสอบบน bench ก่อนใช้จริง:**
- คำสั่งค่าที่อันตรายที่ลูกค้าส่งตรงทาง REST ถูกทิ้ง และบอร์ดไม่เปลี่ยนค่า
- ทางของร้านส่งถึงบอร์ด และผลกลับมาที่ `apply_result`
- ลูกค้าอ่านหรือเขียน asset ของร้านไม่ได้

### 7.1 ค่าสด ค่าเก่า และติดต่อไม่ได้

- ค่าสดมาจาก WebSocket ของ ThingsBoard (`/api/ws`) ส่วนข้อความ "อัปเดตทุก 30 วินาที" ต้องตรงกับรอบจริงของบอร์ด
- **ค่าเก่า:** เมื่อค่าล่าสุดเก่ากว่า 90 วินาที (3 รอบ) แสดงป้าย "ค่าเก่า" และเวลาของค่า
- **ติดต่อไม่ได้:** เมื่อ `active` เป็น false จะแสดงจอ ข3 และกดสั่งงานไม่ได้
  - **ตั้ง `inactivityTimeout` ของบอร์ดเป็น 180 วินาทีใน `tb_setup.py` (ผมตัดสินเอง):** ถ้าไม่ตั้ง ThingsBoard ใช้ค่าเริ่มต้นราว 10 นาที ลูกค้าจะเห็นว่าบ่อยังปกติทั้งที่บอร์ดหลุดไปแล้ว
  - ระหว่างที่ค่าเป็นค่าเก่าแต่ `active` ยังเป็น true ยังสั่งงานได้ แต่ป้าย "ค่าเก่า" ยังแสดงอยู่
- ตัวเลขที่วิ่งต้องวิ่งจากค่าเก่าไปค่าใหม่เท่านั้น ห้ามวิ่งจาก 0

### 7.2 คำสั่งและผลลัพธ์

- **ใช้ RPC แบบ two-way ทุกคำสั่ง** และอ่าน `ok` กับ `error` จากคำตอบ ห้ามแสดงว่าสำเร็จก่อนได้คำตอบ
- **error code ต้องแปลเป็นภาษาไทยที่บอกวิธีแก้:** เช่น `dry_run_locked` ใช้ข้อความ "ปั๊มถูกล็อก" และพาไปจอ ข2 ส่วน `busy` และหมดเวลาใช้ข้อความ "บอร์ดยังไม่ตอบ ยังไม่ได้ทำ" ตาราง code อยู่ใน `docs/firmware/device-api.md` ข้อ 2–8
- **ห้ามส่งคำสั่งซ้ำเองเมื่อหมดเวลา:** บอร์ดกันคำสั่งซ้ำได้แค่ 30 วินาที (ข้อ 10 ของ device-api)

## 9. โครงสร้างและเครื่องมือ

**ตัดสินแล้ว**

- PWA ทำด้วย plugin ของ Vite มี manifest และ service worker ที่เก็บเฉพาะไฟล์ของแอป ไม่เก็บข้อมูลบ่อ เพื่อไม่ให้แสดงค่าเก่าแบบเงียบๆ

## 13. งานเฟิร์มแวร์ (ผู้ใช้อนุมัติตัวเลขและ F3 เมื่อ 2026-11-24)

ทำใน branch ของเฟิร์มแวร์แยกจากตัวแอป แต่ต้องแฟลชหรืออัปเดตทาง OTA ให้บอร์ดลูกค้าก่อนปล่อยแอปให้ลูกค้าใช้

### F1. แคบขีดปลอดภัยของการกันปั๊มเดินแห้ง

แก้ค่าคงที่ใน `dry_run_logic.h` และเพิ่มการตรวจผลรวมใน `dry_run_config_validate`

| ค่า | ตอนนี้ | เสนอ | เหตุผล |
|---|---|---|---|
| `prime_sec` เวลารอน้ำเต็มท่อ | 1..600 | 5..120 | ถ้าน้ำใช้เวลาเกิน 2 นาทีกว่าจะเต็มท่อ แปลว่าท่อหรือปั๊มมีปัญหา ควรให้ช่างแก้ ไม่ใช่ขยายเวลารอ |
| `dry_trip_sec` เวลาเดินแห้งก่อนตัด | 3..120 | 3..30 | หลังผ่านช่วงรอน้ำแล้ว น้ำไม่ไหลเกิน 30 วินาทีถือว่าแห้งจริง |
| ผลรวม `prime_sec` + `dry_trip_sec` | ไม่ตรวจ | ไม่เกิน 150 | เดินแห้งได้ไม่เกิน 2.5 นาทีต่อรอบ และรวมทุกรอบไม่เกินราว 15 นาที |
| `retry_wait_min` เวลารอก่อนลองใหม่ | 1..240 | 1..60 และเพดานของการรอแบบทวีคูณก็เป็น 60 | ปั๊มหยุดนานเกิน 1 ชั่วโมงอันตรายต่อปลา |
| `max_retries` | 0..5 | คงเดิม | |

ผู้ใช้อนุมัติตัวเลขในตารางแล้ว ถ้าภายหลังคู่มือปั๊มที่ร้านติดตั้งบอกว่าเดินแห้งได้สั้นกว่านี้ ให้แก้ค่าคงที่เหล่านี้ที่เดียว

**การย้ายค่าเก่า (สำคัญ):** ห้ามให้บอร์ดที่เก็บค่านอกช่วงใหม่ (เช่น `prime_sec` = 300) ตกไปใช้ค่าเริ่มต้นตอนเปิดเครื่อง เพราะค่าเริ่มต้นจะปิดการกันปั๊มเดินแห้งเงียบๆ
- ให้บีบแต่ละค่าเข้าขอบที่ใกล้ที่สุด แล้วคงค่า `enabled` เดิมไว้
- `protection.get` รายงาน `config_source` เป็นหนึ่งใน `"stored"`, `"clamped"`, `"defaults"` (ไม่เคยบันทึก) หรือ `"defaults_after_error"` (blob เสียหรืออ่านล้ม ใช้ค่าเริ่มต้นเหมือนเดิม) แอปเตือนช่างเมื่อเป็น `"clamped"` หรือ `"defaults_after_error"`

ตัวแนะนำ `prime_sec` จากการวัด (`dry_run_suggest_prime_sec`) ถูกบีบตามเพดานใหม่อยู่แล้ว ถ้าค่าที่วัดได้ชนเพดาน แอปต้องบอกช่างว่า "น้ำเข้าท่อช้าเกินไป ให้ตรวจท่อและปั๊ม"

### F2. บอร์ดบอกขีดของตัวเอง

- `protection.get` ส่ง `limits{prime_sec:[min,max], dry_trip_sec:[...], retry_wait_min:[...], max_retries:[...]}` เหมือนที่ `cooling.config.get` ส่ง limits อยู่แล้ว ไม่ต้องส่งเพดานของผลรวม เพราะช่วงของสองค่ารวมกันไม่เกิน 150 อยู่แล้ว
- ค่านี้ไปถึง ThingsBoard ใน attribute `cfg_protection` เอง แอปจึงไม่ต้องเขียนตัวเลขตายตัว ช่องแก้ค่าในจอ จ2 ใช้ช่วงจากที่นี่
- ปรับ `docs/firmware/device-api.md` ข้อ 3 ให้ตรงด้วย

### F3. หยุดปั๊มแบบตั้งเวลาเปิดกลับ

- `pump.control` รับ `resume_after_min` (5..120) เมื่อ `action` เป็น `"stop"` บอร์ดหยุดปั๊มทันที แล้วเปิดเองเมื่อครบเวลา
- การเปิดตอนครบเวลาใช้ทางเดียวกับ `pump.start` การตรวจกันปั๊มเดินแห้งจึงยังทำงาน และถ้าปั๊มถูกล็อกอยู่จะไม่เปิด
- `pump.start` หรือ `pump.stop` ที่ไม่มี `resume_after_min` ยกเลิกเวลานั้น ส่วนการหยุดแบบไม่มีกำหนดยังทำได้เพื่องานซ่อม
- `pump.status` มี `system_water.resume_in_sec` (0 = ไม่มีกำหนด) และส่งเป็น status telemetry `pump_resume_sec`
- `contract_version` ขึ้นเป็น 2 แอปแสดงตัวเลือกหยุดแบบตั้งเวลาเฉพาะบอร์ดที่เป็น 2 ขึ้นไป
- **ไม่เก็บเวลาข้ามการรีสตาร์ต:** ถ้าบอร์ดรีสตาร์ตระหว่างหยุดชั่วคราว จะทำตาม `water_auto_start` ตามปกติ ซึ่งเอนไปทางให้น้ำหมุน
- จอ ข5 จึงมีตัวเลือก 15 นาที / 30 นาที / 1 ชม. / หยุดจนกว่าจะเปิดเอง

### ทดสอบ

- เพิ่ม test ใน `firmware/test/sensor_selftest/main/test_dry_run.c` สำหรับขอบใหม่ ผลรวม การบีบค่าเก่า และ blob เสีย
- เพิ่ม test ตัวจับเวลาเปิดกลับของ F3 ในส่วน logic ที่ไม่ขึ้นกับ hardware
- bench: ตั้งค่านอกช่วงผ่านหน้าเว็บของบอร์ดต้องถูกปฏิเสธ แฟลชทับบอร์ดที่มีค่าเก่านอกช่วงแล้วการกันยังเปิดอยู่ และหยุด 15 นาทีแล้วปั๊มเปิดเอง

## 14. ข้อเสนอที่รอผู้ใช้ยืนยัน (ถ้าไม่ตอบ ผู้สร้างใช้ค่าที่เขียนไว้)

1. **ชุดเวลา 1 / ชุดเวลา 2 ของปั๊มเรียกตามลูกลอย:** ชุด 1 ใช้เมื่อลูกลอยอยู่ล่าง ชุด 2 ใช้เมื่อลูกลอยยกขึ้น
2. **ค่าไฟประมาณ:** ใช้อัตราต่อหน่วยที่ลูกค้าตั้งเอง ค่าเริ่มต้น 5 บาท
3. **ชื่อร้าน เบอร์ช่าง และที่อยู่เซิร์ฟเวอร์:** เจ้าของร้านกรอกในแอป แล้วแอปคัดลอกชื่อร้านกับเบอร์ช่างลง attribute ของ Customer ทุกราย เพราะ Customer User อ่าน attribute ของ tenant ไม่ได้ (ผมตัดสินเอง)
4. **รูปบ่อจริงของลูกค้า:** รอบนี้ใช้ภาพปลาคาร์ปภาพเดียวกันทุกบ่อ

## 15. ที่ผู้สร้างต้องตรวจก่อนทำ

- **ปุ่ม "ปลดล็อกและเปิดปั๊ม":** ตรวจแล้ว ทางออกจาก LOCKED คือ `alarms.ack` บน alarm ของระบบกันปั๊มเดินแห้ง (`ALARM_SYSTEM_ID_DRY_RUN` ซึ่ง `dry_run_guard.c` ลงทะเบียนไว้กับ `on_alarm_ack`) จากนั้นจึงส่ง `pump.start` ผู้สร้างต้องหา id ของ alarm นี้จาก `alarms.status` แทนการเขียนตัวเลขตายตัว
- **ผูกบอร์ดต้องใช้อะไรบ้าง:** บอร์ดลงทะเบียนเองด้วย provision key ดังนั้นจอ จ4 อาจไม่ต้องแสดง token ให้ตรวจขั้นตอนจริงใน `thingsboard/README.md` แล้วปรับจอให้ตรง
- **ช่วงปกติของเกจ:** ถ้าบอร์ดไม่มีกฎ alarm ของค่านั้น ให้ใช้ค่าเริ่มต้น (อุณหภูมิ 24–28°, pH 7.0–8.2) แล้วติดป้ายว่า "ยังไม่ได้ตั้ง"
- **ชื่อ key ใน telemetry:** ตรวจกับ `firmware/components/uplink_format/uplink_format.c` ก่อนใช้ ห้ามเดาจากเอกสารนี้อย่างเดียว
