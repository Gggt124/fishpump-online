## 1. สิ่งที่ผมทำเองได้และผลที่ได้

| ขั้นตอน | ผล |
|---|---|
| Build และ flash ลง COM12 (`idf.py -p COM12 flash`) | สำเร็จ เขียน 1,778,320 ไบต์ hash ตรง hard reset ผ่าน RTS |
| Boot ถึง "System Ready" | ผ่าน ไม่มี panic ไม่วน reboot OTA ตรวจผ่านเป็น VALID |
| Alarm engine | ขึ้น `13 rules loaded, storage defaults-missing` (13 preset ปิดทั้งหมด ตามที่ออกแบบ) |
| Uplink | ขึ้น `uplink ready (no transport; interval 30 s)` |
| Flow switch init | ไม่มี error ใน log (flow switch log เฉพาะตอนสถานะเปลี่ยน จึงไม่เห็นบรรทัดตอนบูต) |
| ความนิ่งของหน่วยความจำ ดู ~85 วินาที | `heap_free` นิ่งที่ 178,368 `heap_min` 176,444 ไม่ลดลง `tasks=19` |
| Fault ของเซนเซอร์ที่ไม่ได้ต่อ | PT100, SEN0708, PZEM ทั้งสองช่อง รายงาน FAULT ถูกต้อง ไม่ crash และไม่มีกฎไหนทำงานเพราะ preset ปิดอยู่ |

**ที่ผมยืนยันไม่ได้:** ทุกอย่างที่ต้องผ่านหน้าเว็บ (ต้อง join WiFi ของบอร์ด ซึ่งตัดอินเทอร์เน็ตเครื่องคุณ) และทุกอย่างที่ต้องต่อฮาร์ดแวร์จริง
ข้อสังเกตจาก log: จำนวน task = 19 ผมไม่มีค่าก่อนหน้า branch มาเทียบ จึงยังยืนยันไม่ได้ว่าเพิ่มขึ้น 3 ตัวตามแผน

## 2. สิ่งที่คุณต้องทำเอง

ทำตาม [bench-test-alarms.md](../../bench-test-alarms.md) ตามลำดับหัวข้อ ผมสรุปว่าแต่ละข้อต้องใช้อะไร:

| 2 เริ่มจากศูนย์ | เบราว์เซอร์อย่างเดียว | |
| 3 กฎ pH ไม่ตอบ | **ไม่ต่อ SEN0708** | ตอนนี้บอร์ดอยู่ในสภาพนี้อยู่แล้ว |
| 4 กฎ uptime | เบราว์เซอร์อย่างเดียว | ไม่ต้องใช้ฮาร์ดแวร์ |
| 5 รับทราบและ latch | เบราว์เซอร์อย่างเดียว | |
| 6 กฎมี gate | สั่ง start/stop ปั๊มน้ำ | |

| 9 Uplink preview | เบราว์เซอร์ | ข้อ 9.3 ต้องก่อเหตุเกิน 32 ครั้ง |

| 11 ระบบเดิมไม่พัง | เบราว์เซอร์ + ปั๊ม | ปั๊ม cooling ต้องไม่ผิดปกติ |

ถ้าข้อไหนไม่ผ่าน ให้จดเลขข้อ ข้อความที่เห็น และ serial log ช่วงนั้น แล้วส่งมา ผมจะแก้ทีละ commit

## 3. ผลรีวิวโค้ดทั้ง branch

รีวิวโดย Claude ในเซสชันนี้ ระดับ high ไล่อ่านโค้ดหลักทั้งหมดของ branch (alarm_eval, alarm_engine, uplink, uplink_format, signal_registry, alarm_json/validate/blob/presets, flow_switch, nvs_store, แฮนด์เลอร์ใน web_server.c และจุดที่ JS ใส่ค่าลง DOM) ยังไม่ได้แก้อะไรจากผลนี้
อ่านโดยผู้เขียนเดิมคนเดียวกับที่เขียนโค้ด ยังไม่ใช่รีวิวจากคนอื่น ผลที่ได้เป็นผลเสริมไม่ใช่ตัวแทน

พบ 9 ข้อ ไม่มีข้อที่ทำให้ระบบพังตอนนี้ ข้อที่น่ากังวลที่สุดคือข้อ 1 และ 2 ซึ่งจะเป็นปัญหาตอนต่อยอด

| # | ความรุนแรง | ที่ไหน | ปัญหา |
|---|---|---|---|
| 1 | กลาง | `uplink.c:96` | `s.sink` ถูกอ่านโดย task uplink โดยไม่ล็อก ขณะ `uplink_set_sink` เขียนใต้ล็อก ถ้าต่อ/ถอด MQTT พร้อมกับการส่งอาจเห็น struct ครึ่งๆ กลางๆ ตอนนี้ยังไม่มี transport จึงยังไม่เกิด แต่จะเกิดในโปรเจกต์ MQTT |
| 2 | กลาง | `alarm_blob.c:20` | บันทึกกฎลง NVS ด้วยการ memcpy struct ทั้งก้อน และเช็คแค่ความยาวตรงเป๊ะ ถ้าวันหน้าเพิ่มฟิลด์ใน `alarm_rule_t` กฎที่ผู้ใช้จูนไว้ทั้งหมดจะถูกทิ้งแล้วกลับเป็น preset ที่ปิดอยู่เงียบๆ หลัง OTA |

| 6 | ต่ำ-กลาง | `web_server.c:5690` | `ack` ที่ล้มเหลวทุกแบบถูกบอกว่า not_found, `ack_all` ที่ calloc ไม่ได้ตอบ ok พร้อม acked:0 เงียบๆ ตัวไฟ LED จะยังกระพริบโดยไม่มีข้อความบอก |
