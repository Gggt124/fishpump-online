# งานที่รอทำต่อ (หลัง frontend)

อัปเดต: 2026-11-21 · เฟิร์มแวร์ 0.4.0 บน `main`
ไฟล์นี้รวมทุกอย่างที่ยังไม่ได้ทำ: ข้อทดสอบบนบอร์ด งานที่ต้องมีฮาร์ดแวร์ งานที่เลื่อนไว้ และข้อเล็กที่ตั้งใจไม่แก้
ภาพรวมของงานที่ทำเสร็จแล้วอยู่ใน [`docs/summary.md`](../summary.md) และโครงสร้างเฟิร์มแวร์อยู่ใน [`docs/firmware/reference.md`](../firmware/reference.md)
ประวัติละเอียด (spec, แผน, ผล bench ทุกรอบ) อยู่ใน branch เก็บถาวร `feature/thingsboard-mqtt`

## (a) ทดสอบบนบอร์ดที่ยังค้าง

ขั้นตอนทั้งหมดอยู่ใน [`docs/bench-test-pending.md`](../bench-test-pending.md)

- ไม่ต้องต่อเซนเซอร์:
  - LED staging ทับสีแจ้งเตือน (A1)
  - น้ำกลับมาไหลระหว่างรอลองใหม่ (A2)
  - log ตอนรอ 20 นาที (A3)
  - เปลี่ยน Wi-Fi จาก ThingsBoard แบบเต็ม ต้องมี access point ตัวที่สอง (A4)
  - OTA checksum ไม่ตรง (A5)
  - เวลาที่ ThingsBoard พร้อมหลัง `docker start` (A6)
  - TLS ใบรับรองไม่น่าเชื่อถือ ทำหลังมีเซิร์ฟเวอร์ TLS (A7)
  - แท็บซ่อนจริงบนมือถือ ไม่บังคับ (A8)
- ต้องต่อเซนเซอร์: PZEM ×2 (ปั๊มน้ำและ Chiller), pH SEN0708 พร้อมคาลิเบรต, จูน preset แจ้งเตือน 3 ข้อด้วยค่าจริง, ปั๊มและ flow switch จริงในท่อ (B1–B4)

### บันทึก bench แจ้งเตือนของคุณ (2026-11-16)

ทุกข้อที่คุณจดไว้ในรอบนั้นถูกแก้และทดสอบผ่านบนบอร์ดแล้ว ยกเว้น buzzer บนบอร์ด

| สิ่งที่คุณพบ | ทำแล้ว |
|---|---|
| ปั๊มเดินเป็นรอบแล้วกฎ "ปั๊มน้ำเปิดแต่น้ำไม่ไหล" ไม่ปกป้องปั๊ม และประวัติเกิด/หายสลับกันเต็มไปหมด | ระบบป้องกันเดินแห้ง: ตัดปั๊ม รอลองใหม่แบบ backoff แล้วล็อกจนกดรับทราบ |
| แจ้งเตือนบนเว็บรับรู้ช้าและหลุดง่าย อยากได้กระดิ่ง จุดแดงต้องไม่หายเอง และเหตุวิกฤตต้องแจ้งให้หนักกว่านี้ | กระดิ่งมุมขวาบน จุดแดงค้างจนเปิดดู อัปเดตทุก 3 วินาที overlay วิกฤตพร้อมเสียงจากเบราว์เซอร์ |
| LED เป็นเขียวทั้งที่มีแจ้งเตือนระดับเตือน | LED ตามระดับ: วิกฤตแดงกระพริบ เตือนส้มค้าง ข้อมูลน้ำเงินค้าง |
| คำซ้ำ "รีเลย์ 1 เปิด เปิด", "ลูกลอยลอย เปิด" | ค่าของสัญญาณแบบ bool แสดงเป็น ใช่/ไม่ใช่ |
| คำสั่ง curl ทดสอบความปลอดภัยของ API ใช้ใน PowerShell ไม่ได้ | เขียนใหม่เป็น PowerShell แล้วทดสอบผ่าน |
| log ซ้ำทุกวินาทีตอน PT100 เสีย และบรรทัด E ของ TWDT ตอนบูต | log ครั้งเดียวตอนเริ่มเสียและตอนกลับมา บรรทัด TWDT ไม่เป็น error แล้ว |
| **ยังไม่ทำ:** buzzer บนบอร์ด | ดูข้อ (b) |

## (c) ThingsBoard และแพลตฟอร์ม

- [ ] **การเก็บข้อมูลใน ThingsBoard และการ deploy จริงบน VPS:** ตอนนี้ข้อมูลไม่มีวันถูกลบ ประมาณ 10 GB ต่อปีต่ออุปกรณ์ แผนอยู่ใน [`thingsboard-data-and-deploy.md`](thingsboard-data-and-deploy.md) ทำหลัง frontend ก่อนเปิดใช้กับลูกค้าหลายราย
- [ ] **แก้ก่อนใช้ alarm ของ ThingsBoard ส่งแจ้งเตือนจริง:**
  - เหตุการณ์ที่ส่งเข้า outbox ของ MQTT แล้วอาจหายใน 2 กรณี:
    - ลิงก์หลุดเงียบที่ไม่ใช่ Wi-Fi หลุด เช่นเราเตอร์ค้าง บอร์ดรู้ตัวในประมาณ 45 วินาที แล้วส่งไม่ทันใน 300 วินาทีที่ outbox เก็บไว้
    - การบันทึกการ์ด ThingsBoard ใหม่ ซึ่งทิ้ง outbox
  - ring เหตุการณ์บนบอร์ดมี 32 ช่อง จะเต็มเมื่อ ThingsBoard ล่มนานประมาณ 30 นาทีที่อัตรา 1 event ต่อนาที (bench ล่ม 38 นาทีเสีย event เก่าสุด 9 ตัว ตามดีไซน์)
  - ทางแก้ที่เป็นไปได้:
    - ส่งต่อเหตุการณ์จาก `uplink` หลังได้ ack แล้วเท่านั้น (`MQTT_EVENT_PUBLISHED`)
    - ส่งรายการ alarm ที่ยัง active เป็น attribute ให้ ThingsBoard เทียบเอง
    - ขยาย ring
- [ ] `clearTs` ของ alarm ใน ThingsBoard เป็นเวลาที่เซิร์ฟเวอร์ได้รับ ไม่ใช่เวลาที่หายจริงบนบอร์ด (`startTs` ใช้เวลาของบอร์ดอยู่แล้ว) ถ้าต้องการเวลาจริง ให้ rule chain ใส่ `ts` ของเหตุการณ์ลงใน alarm details
- [ ] ThingsBoard ไม่เก็บ `alarm_event` เป็น timeseries ถ้า frontend อยากได้ประวัติ ต้องอ่านจาก alarm ของ ThingsBoard
- [ ] ThingsBoard ไม่เก็บสมาชิกที่เป็น null ใน attribute แบบ JSON (เช่น `hardware_map.pending`) frontend ต้องถือว่า field ที่หายไปคือ null
- [ ] ตอนต่อกลับพร้อม event ค้างเต็ม ring outbox ของ MQTT เต็มชั่วคราว: `rules attribute send failed` 2 ครั้ง และ `status send failed` 1 ครั้ง บอร์ดลองใหม่เองแล้วผ่าน ทางแก้: ข้าม `do_state` ใน tick ที่เพิ่งส่ง identity/rules
- [ ] กดบันทึกการ์ด ThingsBoard ขณะลิงก์อยู่ใน backoff มีผลช้าสุดประมาณ 5 วินาที สาเหตุยังไม่ยืนยัน ที่น่าจะเป็นคือ `esp_mqtt_client_destroy` ใน `task_teardown`
- [ ] `hwm_alarm` ต่ำสุด 2136 ระหว่าง ThingsBoard ล่ม (รอบก่อน 2600–2712) ยังเกินงบ 512 สาเหตุยังไม่ชัด
- [ ] `heap_min` อยู่ที่ประมาณ 105–108 KB เกินงบ 100 KB ไม่มาก ต้องวัดใหม่เมื่อเปิด TLS จริง ถ้าตึง ให้ mbedTLS ใช้ PSRAM (`CONFIG_MBEDTLS_EXTERNAL_MEM_ALLOC`)
- [ ] **dashboard ทดสอบ:** ปุ่ม `wifi.connect` ส่ง params ตัวอย่าง (`แก้ก่อนส่ง`) ได้ ทำให้บอร์ด stage เครือข่ายที่ไม่มีอยู่และรีบูตฟรี 2 ครั้ง ควรให้ widget ไม่ยอมส่งค่าตัวอย่าง หรือให้เฟิร์มแวร์ปฏิเสธ SSID ที่ไม่เห็นใน scan ล่าสุด
- [ ] การย้อนกลับเมื่อรหัส Wi-Fi ผิดใช้เวลา 180 วินาที ไม่ใช่ 30 วินาที เพราะ `wifi_manager` ถอยไปเครือข่ายเดิมเองก่อน ปลอดภัยแต่ช้า ทางแก้: ให้ timer 30 วินาทีดูว่าต่ออยู่บน SSID ที่ stage ไว้
- [ ] `pump.config.set` มีเพดาน params 512 ไบต์ เท่ากับ body ของ HTTP กรณียาวสุดของเว็บแอปตอนนี้คือ 475 ไบต์ ถ้าเพิ่ม key ใน config ต้องเช็กเพดานนี้
- [ ] การอัปโหลดเฟิร์มแวร์ผ่านเว็บ (`POST /api/ota`) มีเพดาน 1,966,080 ไบต์ แต่อิมเมจปัจจุบันประมาณ 2.06 MB จะได้ 413 `file_too_large` ต้องปรับเพดานให้ตรงกับ slot (0x380000) การอัปเดตผ่าน ThingsBoard ไม่ติดเพดานนี้
- [ ] `tb_ota.py`: เมื่อ upload ล้ม ThingsBoard ทิ้ง package ว่างไว้ ควรลบให้เอง
- [ ] ไม่มีที่รายงาน HWM ของ task `tb_ota` ทางแก้: log ตอน task จบ หรือใส่ใน `BOARD_DIAG`
- [ ] log `OTA firmware validated (PENDING_VERIFY -> VALID)` ขึ้นแม้สถานะเป็น VALID อยู่แล้ว ทำให้อ่าน log สับสน
- [ ] โปรไฟล์ Wi-Fi `Ggggg` บนบอร์ดทดสอบอาจเก็บรหัสที่ผิดไว้ (เหลือจากการทดสอบแทน J4)
- [ ] ตามแผนแพลตฟอร์ม: กฎอยู่ในเฟิร์มแวร์ ส่วน ThingsBoard เก็บข้อมูลและส่งแจ้งเตือน รองรับหลายลูกค้าและหลาย firmware (`identity` มี `fw_type` และ `contract_version` ไว้สำหรับเรื่องนี้)

## (d) ข้อเล็กที่ตั้งใจไม่แก้ (minor ที่เลื่อนไว้) พร้อมเหตุผลบรรทัดเดียว

ไม่มีข้อไหนกระทบความปลอดภัยของปั๊มหรือทำให้ข้อมูลหาย เว้นแต่ที่ระบุ

### จากรอบเก็บงานก่อน MQTT (ledger ตามลำดับ task)

**Task 1 (กฎ PENDING / LED level)**
- ไม่มี test ว่าสถานะ FAULT เคลียร์ตัวนับ holding — เหตุผล: โค้ดเคลียร์ทุก verdict ที่ไม่ใช่ HOLD ตามเดิมและมี test ครอบคลุมทางอื่น
- ไม่มี test ตอนตัวจับเวลา hold วนรอบ (wrap) — เหตุผล: ใช้ลบแบบ unsigned เหมือนทุกที่ ผลต่างไม่เกินตัวเลขที่เล็กมาก
- การตรวจ verify เป็น substring อ่อน — เหตุผล: ตัวพฤติกรรมจริงมี test ใน QEMU ตรวจแล้ว

**Task 2 (blob v2)**
- test กรณี record เล็กลงแทบไม่ได้ตรวจอะไร — เหตุผล: spec ต้องการแค่ไม่อ่านเกินและกฎที่ได้ต้องผ่านการตรวจ ผู้ตัดสินให้คงไว้ (ต้นทุนถ้าผิด: test อ่อน)
- ตัวเลข `4` เป็น literal ใน test — เหตุผล: เป็นแค่ขนาด header ของ v1 ใน test เท่านั้น
- คอมเมนต์ header พูดว่า "bad length" — เหตุผล: คอมเมนต์ไม่ตรงนิดเดียว ไม่กระทบพฤติกรรม

**Task 3 (uplink)**
- `connected_cache` อัปเดตเฉพาะตอน `do_attributes` ทำงาน (ค้างค่าเก่าตอน hub ล่ม) — เหตุผล: เป็นข้อมูลแสดงผลใน preview เท่านั้น
- ตอนนาฬิกามาถึงขณะที่เหตุการณ์ถูกปล่อยไปแล้ว ไม่มี log บอกว่าโหมดไม่มี `ts` จบ — เหตุผล: log อย่างเดียว ไม่กระทบข้อมูล
- preview แสดง `waiting_for_clock:false` ตอนถือเหตุการณ์อยู่แต่ sink หลุด — เหตุผล: ตอนนี้ไม่มี sink จริง ค่อยตรวจกับ MQTT
- การตัดสินว่ามี `ts` หรือไม่ซ้ำกันสองที่ (ผลของ step กับ `unix_now`) — เหตุผล: ซ้ำเชิงโครงสร้าง ผลตรงกัน
- `pending_events` ถูกเขียนนอก `s.lock` — เหตุผล: เป็น uint32 ตัวเดียว ฝั่งอ่านใช้แสดงผล race ไม่เป็นอันตราย (โค้ดเดิม)

**Task 4 (LED)**
- แจ้งเตือนเตือน/ข้อมูลที่ยังไม่รับทราบ **บังสีเขียว "AP เปิด"** — เหตุผล: ตั้งใจตามลำดับใน spec และทดสอบที่ `bench-test-pending.md` ข้อ A1
- คอมเมนต์ของ `last_critical_seq` ควรเขียนว่า "ตั้งแต่บูตนี้" — เหตุผล: คอมเมนต์เท่านั้น
- LED ข้อมูลสีน้ำเงินค้างคล้ายสี recovery AP — เหตุผล: ต่างกันที่ค้าง/กระพริบ และ recovery AP ทับแจ้งเตือนเสมอ

**Task 5 (log/diag)**
- ไม่ตรวจค่าที่คืนจาก `esp_task_wdt_add(NULL)` ในทางที่ตั้งค่าแล้ว — เหตุผล: โค้ดเดิมก็ไม่ตรวจ ถ้าล้มจะไม่มี watchdog ของ task หลักแต่ไม่กระทบการทำงาน
- regex ของ verify (PT100 guard, เก็บ handle) เปราะ — เหตุผล: เป็นตัวตรวจเท่านั้น ถ้าโค้ดเปลี่ยนรูปจะเห็นเป็นผลไม่ผ่านให้แก้เอง
- handle ของ task ค้างถ้า init ซ้ำ — เหตุผล: ไม่มีทาง init ซ้ำในเฟิร์มแวร์นี้ ไม่มี task ถูกลบ

**Task 6 (dry-run guard)**
- guard ยังไม่ init ทำให้ได้ 409 "ต้อง stop ปั๊มก่อน" ซึ่งชวนเข้าใจผิด (INVALID_STATE) — เหตุผล: ของเดิม และเกิดเฉพาะ init ล้มซึ่งบอร์ดจะไม่ใช้งานอยู่แล้ว
- log กู้คืนหลัง retry อาจเอ่ยการกระทำที่ถูกแทนไปแล้ว — เหตุผล: log อย่างเดียว สถานะสุดท้ายถูกต้อง
- ตอบ `unavailable` แทน `measure_unavailable` ตาม spec §5 เมื่อ start ผิดพลาดแบบอื่น — เหตุผล (Ruling): ใช้รหัสเดียวกับ 503 อื่นและสาขานี้ตอนนี้เข้าไม่ถึง (ต้นทุนถ้าผิด: เปลี่ยนสตริงเดียว)

**Task 7 (UI การ์ดเดินแห้ง)**
- poll ตอนแท็บกลับมามองเห็นอาจซ้อนกับ poll ที่ค้างอยู่ (GET เกิน 1 ครั้ง) — เหตุผล: เป็นแค่คำขอ GET เพิ่ม 1 ครั้ง

**Task 8 (กระดิ่ง/overlay)**
- การปิด overlay หลังรับทราบใช้สรุปที่จับไว้ตอนกดปุ่ม — เหตุผล: คิดตามเหตุผลแล้วว่าถูกต้อง แต่ยังไม่ได้ทดสอบ และผลเสียถ้าผิดคือ overlay เด้งซ้ำหนึ่งรอบ
- overlay ไม่มี Tab trap (กด Tab ออกไปโฟกัสหน้าหลังได้) — เหตุผล: ไม่กระทบความปลอดภัย ปุ่มทั้งสองอยู่ในลำดับโฟกัสแรกและ overlay ปิดได้ด้วยเมาส์
- session หมดอายุโดยไม่เปลี่ยนหน้า overlay/เสียงจะค้างจนกว่าจะเปลี่ยนเส้นทางครั้งถัดไป — เหตุผล: เกิดเฉพาะ session หมดอายุตอนเปิด overlay ค้างไว้ และหายเองเมื่อ route เปลี่ยน
- `<dialog>` ของ confirm อยู่ top layer จึงเรียงทับ overlay — เหตุผล: ได้ผลที่ต้องการ (กล่องยืนยันรับทราบต้องมองเห็นเหนือ overlay) ไม่ใช่ข้อบกพร่อง

### จากระบบป้องกันปั๊มเดินแห้ง (รีวิวส่วน 4 และ 7) ที่ Task 6–7 ไม่ได้แก้

(ข้อที่แก้แล้วในรอบนี้: การซ่อม raise/clear ของแจ้งเตือน, การอ่าน flow switch ไม่ได้ตอนวัด, ช่วงตัวเลขในการ์ด, ข้อความอธิบายเมื่อช่วงเปิดสั้น, poll ตอนซ่อนแท็บ, ฟอร์มไม่เติมค่าหลัง 503, poll วัดล้มเหลว, ข้อ "4." ซ้ำ, ขั้น bench stop ระหว่าง WAIT)

- Task 3: verify ไม่พิสูจน์ว่าไม่มี callback ก่อน Give; `on_ack` เป็น NULL ได้ `acked:1`; คอมเมนต์เก่า `alarm_presets.c:18-19`; engine ไม่มี runtime test — เหตุผล: ตัวตรวจ/คอมเมนต์ และ engine ต้องมี FreeRTOS+NVS จึงทดสอบบน QEMU ไม่ได้
- Task 4: regex verify ผ่านด้วยคอมเมนต์; เงื่อนไข inhibit เขียนซ้ำ 3 ที่; `on_phase` ซ้ำกับ `start_phase`; header ไม่อธิบายกรณี `resume=false && running`; คอมเมนต์ `:429`; ไม่มี log ตอน inhibit; `active_set` หยุดเปลี่ยนตอน inhibited; `water_test(false)` ถูกปฏิเสธเมื่อ faulted; ไม่มี runtime test ของ `pump_control`; `notify_state_changed` ถูกเรียกใต้ mutex — เหตุผล: ทั้งหมดไม่กระทบพฤติกรรม และ "ห้ามเปลี่ยนพฤติกรรมปั๊มในรอบนี้"

- Task 8: regex ตรวจลำดับ lock ยังอ่อน; ไม่มีคอมเมนต์ว่าการตรวจบนสำเนาพึ่ง `write_lock` — เหตุผล: ตัวตรวจ/คอมเมนต์
