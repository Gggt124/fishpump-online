## เจตนา

## เป้าหมาย

1. ค่าของสัญญาณแบบ bool อ่านได้ตรงความหมาย ไม่ซ้ำซ้อน
2. คนรู้ตัวเร็วว่ามีแจ้งเตือน ทั้งบนคอมและมือถือ และไฟบนบอร์ดบอกระดับได้
3. firmware พร้อมให้ MQTT ต่อเข้ามาโดยไม่มีจุดที่รู้อยู่แล้วว่าจะพัง
4. log ตอนบูตและตอนเซนเซอร์เสียไม่รก
5. ข้อเล็กของระบบเดินแห้งที่ผู้ใช้จะเห็นถูกแก้
6. มี checklist สำหรับรอบนี้ และมีไฟล์รวมงานที่ต้องใช้ฮาร์ดแวร์

## ไม่ทำในรอบนี้

- MQTT, SNTP และการต่อ Wi-Fi บ้าน (โปรเจกต์ถัดไป)
- ระบบป้องกัน chiller (ตกลงกันว่าเลื่อนไว้)
- buzzer บนบอร์ด (ต้องมีฮาร์ดแวร์ ใส่ในไฟล์งานค้าง)
- การจูน preset ไฟฟ้าและ pH (ต้องต่อเซนเซอร์)
- flash, push, merge

## สิ่งที่ห้ามเกิด

- การแก้รอบนี้ทำให้ระบบเดินแห้ง การคุมปั๊ม หรือ cooling เปลี่ยนพฤติกรรม
- กฎที่ผู้ใช้ตั้งไว้ในบอร์ดหายหลัง OTA ครั้งนี้ ต้อง migrate blob เดิมได้
- หน้าเว็บส่งคำขอถี่จนบอร์ดช้า

## การออกแบบทีละเรื่อง

### 1. ค่าสัญญาณ bool เป็น ใช่/ไม่ใช่ (รอบ A, bench ข้อ 4)

**(Claude ตัดสิน)** ใช้ทางแรกที่บันทึกไว้ คือแสดงค่า bool เป็น **ใช่/ไม่ใช่** ทุกที่ในหน้าแจ้งเตือน
- จุดที่เปลี่ยน: "ค่าตอนนี้", คอลัมน์ค่าในประวัติ, คำอธิบายกฎ (`= ใช่` / `= ไม่ใช่`) และเงื่อนไข "เฉพาะตอน ... ใช่/ไม่ใช่"
- ข้อความในตัวเลือกเงื่อนไขเปลี่ยนเป็น "เป็นจริง (ใช่)" / "เป็นเท็จ (ไม่ใช่)"
- ตัวเลือก "เฉพาะตอน" ในฟอร์มก็ต้องใช้คำเดียวกัน

เหตุผล: ชื่อสัญญาณเป็นประโยคอยู่แล้ว ("ลูกลอยลอย") การเปลี่ยนชื่อสัญญาณ 10 กว่าตัวกระทบ uplink และ API มากกว่า

ค่าแจ้งเตือนของระบบ (rule_id ≥ 65000) ยังแสดง "ครั้งที่ n" เหมือนเดิม

### 2. การแจ้งเตือนที่รับรู้ง่าย (รอบ C, bench ข้อ 2 และ 3)

**2.1 กระดิ่ง (Claude ตัดสิน)**
- ปุ่มกระดิ่งลอยมุมขวาบนของหน้า แสดงทุกหน้าหลัง login ทั้งคอมและมือถือ เดิมบนมือถือรายการแจ้งเตือนซ่อนอยู่ในเมนู "เพิ่มเติม"
- ตัวเลขบนกระดิ่งใช้สูตรเดิมของ badge: แจ้งเตือนที่ active บวกเหตุการณ์ที่ยังไม่เห็น
- เหตุการณ์ที่ยังไม่เห็นจะ**ไม่หายเอง** จนกว่าจะกดเปิดกระดิ่งหรือเข้าหน้าแจ้งเตือน
- กดกระดิ่งแล้วเปิดแผงที่มีเหตุการณ์ล่าสุด 5 รายการ และปุ่ม "ดูทั้งหมด" ไปหน้า `/alarms`
- ปุ่ม "เพิ่มเติม" บนมือถือมีจุดแดงด้วยเมื่อมีเหตุการณ์ที่ยังไม่เห็น
- ชื่อแท็บเบราว์เซอร์ขึ้นต้นด้วย `(n)` เมื่อตัวเลขมากกว่า 0

**2.2 อัปเดตเร็วขึ้น**
- สรุปแจ้งเตือนดึงทุก 3 วินาที จากเดิม 10 วินาที ทำเฉพาะตอนแท็บเปิดอยู่ (คำขอนี้เล็ก ตอบจาก RAM)
- เมื่อกลับมาที่แท็บ ดึงทันที
- SSE `alarm` ยังทำงานเหมือนเดิมเมื่อมีช่องว่าง

**2.3 เหตุวิกฤต (Claude ตัดสิน)**
- เมื่อมีเหตุวิกฤตใหม่ที่ยังไม่รับทราบ หน้าเว็บขึ้นหน้าต่างเต็มจอสีแดง
- มีสองปุ่ม:
  - **"รับทราบทั้งหมด"** เรียก ack แบบ all
  - **"ปิดไว้ก่อน"** ปิดเฉพาะในเบราว์เซอร์นี้ ไฟบนบอร์ดยังกระพริบ
- หน้าต่างนี้ขึ้นครั้งเดียวต่อเหตุวิกฤตหนึ่งครั้ง ระบุด้วย `last_critical_seq` ใหม่ใน summary
- เสียงเตือน:
  - เล่นด้วย WebAudio เป็นบี๊บสั้น 3 ครั้ง ทุก 5 วินาที ระหว่างที่หน้าต่างเปิดอยู่
  - ปิดเสียงได้จากสวิตช์ในหน้าแจ้งเตือน ค่าเก็บใน localStorage และค่าเริ่มต้นคือเปิด
  - เบราว์เซอร์ไม่ยอมให้เล่นเสียงก่อนผู้ใช้แตะหน้าเว็บ ถ้าเล่นไม่ได้หน้าต่างยังขึ้นตามปกติ
- firmware เพิ่ม `last_critical_seq` ใน `alarm_engine_summary_t` และใน `/api/alarms/summary` คือเลข seq ของเหตุการณ์ raised ล่าสุดที่เป็นวิกฤต และเป็น 0 ถ้ายังไม่มี

**2.4 สีไฟ LED ตามระดับ (Claude ตัดสิน ตามที่ผู้ใช้เสนอ)**

| สถานะ | ไฟ RGB |
|---|---|
| มีวิกฤตที่ยังไม่รับทราบ | แดงกระพริบ 1 Hz (เดิม) |
| มีเตือนที่ยังไม่รับทราบ | ส้มค้าง (เดิมเหลือง ผู้ใช้ขอเปลี่ยนหลัง bench 2026-11-18 เพราะเหลืองดูใกล้เขียว) |
| มีข้อมูลที่ยังไม่รับทราบ | น้ำเงินค้าง |
| ไม่มี | เหมือนเดิม: เขียวถ้า AP เปิด ไม่งั้นดับ |

- ลำดับความสำคัญ: ปุ่มกดค้าง, recovery AP, factory reset และ staging ยังมาก่อนทุกสีแจ้งเตือน (เหมือนเดิม) ตามด้วยวิกฤต > เตือน > ข้อมูล
- น้ำเงินค้างต่างจาก recovery AP ซึ่งเป็นน้ำเงิน**กระพริบ**
- หลังรับทราบแล้ว ไฟกลับเป็นสถานะปกติ เพราะนับเฉพาะที่ยังไม่รับทราบ
- `alarm_counts_t` เพิ่ม `warning_unacked` และ `info_unacked`
- ฟังก์ชัน pure `alarm_counts_led_level()` เลือกระดับไฟ และทดสอบใน self-test
- LED ภายนอก (GPIO) ไม่เปลี่ยน

### 3. ก่อน MQTT (รอบ D)

**3.1 รีวิวข้อ 1: `s.sink` ไม่ล็อก**
- เพิ่ม mutex `send_lock` ใน uplink
- task ถือ lock นี้ตลอดการใช้ sink หนึ่งครั้ง (เช็ค connected และ send)
- `uplink_set_sink` ถือ lock เดียวกันตอนเปลี่ยน sink จึงรอการส่งที่ค้างอยู่ให้จบก่อน
- ผลคือหลัง `uplink_set_sink(NULL)` คืนค่า จะไม่มีการเรียก ctx เดิมอีก ตัว transport ปล่อย ctx ได้ปลอดภัย
- `s.lock` เดิมยังใช้คุม buffer preview เหมือนเดิม

**3.2 รีวิวข้อ 2: blob ของกฎไม่มีเวอร์ชันฟิลด์**
- blob เวอร์ชัน 2 header 6 ไบต์: `ver=2, count, next_id(lo, hi), rec_size(lo, hi)` ตามด้วย record ขนาด `rec_size` จำนวน `count` ตัว
- อ่านได้ทั้งสองเวอร์ชัน:
  - **v1 (blob ในบอร์ดตอนนี้):** อ่านแบบเดิม ค่าที่ผู้ใช้ตั้งไว้ไม่หาย
  - **v2:** คัดลอก `min(rec_size, sizeof(alarm_rule_t))` ไบต์ ส่วนที่เหลือเป็นศูนย์ แล้วผ่าน `alarm_rule_validate` เหมือนเดิม
- กติกาต่อไป: ฟิลด์ใหม่ใน `alarm_rule_t` ต่อท้ายเท่านั้น และค่า 0 ต้องหมายถึงค่าเริ่มต้น เขียนไว้เป็นคอมเมนต์ที่ struct
- การเขียนใช้ v2 เสมอ blob v1 จะถูกเขียนใหม่เป็น v2 เมื่อผู้ใช้บันทึกกฎครั้งถัดไป ไม่มีการเขียนตอนบูต

**3.3 รีวิวข้อ 7: timestamp เมื่อไม่มีนาฬิกาจริง**
- uplink ย้อนเวลาเหตุการณ์จาก uptime ได้อยู่แล้ว (`uplink_event_ts`) เมื่อมี wall clock ปัญหาเหลือแค่ตอนส่งก่อนนาฬิกาตั้ง
- **(Claude ตัดสิน)** ขณะ sink ต่ออยู่แต่ยังไม่มีนาฬิกา ให้**ถือ**เหตุการณ์ไว้ใน ring ไม่ส่ง
- ข้อยกเว้น: เมื่อเหตุการณ์ค้างส่ง ≥ `ring_len - 8` (คือ 24 จาก 32) ให้ส่งแบบไม่มี ts ดีกว่าถูกเขียนทับหาย
- ฟังก์ชัน pure `uplink_forward_hold_for_clock(clock_set, pending, ring_len)` ทดสอบใน self-test
- ข้อมูล preview เพิ่ม `"waiting_for_clock": true/false`
- โปรเจกต์ MQTT ต้องตั้ง SNTP แล้วส่ง `wall_clock` ให้ uplink เหมือนเดิม

**3.4 รีวิวข้อ 3: ตัวนับ PENDING เมื่อสัญญาณหายนาน (Claude ตัดสิน)**
- เดิมสัญญาณหายแบบไม่ใช่ fault (HOLD) ไม่เปลี่ยนสถานะ ตัวจับเวลา delay จึงเดินต่อข้ามช่วงที่ไม่มีข้อมูล
- ใหม่: ถ้า HOLD ต่อเนื่อง **≥ 5 วินาที** ขณะ PENDING ให้กลับเป็น NORMAL เมื่อค่ากลับมาก็เริ่มนับ delay ใหม่
- การพลาดครั้งเดียวยังไม่เปลี่ยนอะไรตาม spec เพราะ PZEM poll ทุก 2 วินาที ส่วน pH ทุก 1–2 วินาที
- สถานะ ACTIVE ไม่เปลี่ยนระหว่าง HOLD (เหมือนเดิม)
- ค่าคงที่ `ALARM_HOLD_RESET_MS 5000`
- เพิ่มฟิลด์ใน `alarm_runtime_t` ซึ่งอยู่ใน RAM เท่านั้น จึงไม่กระทบ NVS

### 4. log และ diag (รอบ A, bench ข้อ 6)

- **PT100 fault:** log WARN ครั้งเดียวตอนเริ่มเสีย ไม่ใช่ทุกวินาที log ตอนกลับมาปกติมีอยู่แล้ว
- **TWDT:** เมื่อ `CONFIG_ESP_TASK_WDT_INIT` เปิด ให้ข้ามการเรียก `esp_task_wdt_init` และไป `esp_task_wdt_reconfigure` ตรงๆ บรรทัด `E task_wdt: TWDT already initialized` จะหายไป
- **บรรทัด `[BOARD_DIAG]`:** เพิ่มค่า stack ที่เหลือ (high-water mark) ของ task `alarm_eng`, uplink และ `dry_run_guard` แก้ข้อ "ยังไม่ได้ยืนยัน stack 4096" ในผลระบบเดินแห้ง ถ้าหา task ไม่เจอให้แสดง `-1`

### 5. ข้อเล็กของระบบเดินแห้งที่แก้รอบนี้

**firmware:**
- ถ้า raise หรือ clear แจ้งเตือนของระบบล้มเหลว (เช่น หน่วยความจำไม่พอ) guard ลองใหม่ทุก tick จนสำเร็จ
- อ่าน flow switch ไม่ได้ตอนกด "วัดให้" → ปฏิเสธด้วย 503 `flow_unavailable` (ไม่เริ่มวัด) แทนการข้ามการเช็ค
- `measure_start` error อื่นที่ไม่ใช่กรณีที่รู้จัก → 503 `measure_unavailable` แทน 409

**หน้าเว็บ:**
- ช่องกรอกแสดงช่วงจริง: ผ่อนผัน 1–600, ไม่มีน้ำสะสม 3–120, รอ 1–240, ลองใหม่ 0–5 ทั้ง `min`/`max` และข้อความกำกับ
- การ์ดหยุด poll เมื่อแท็บถูกซ่อน และ poll ทันทีเมื่อกลับมา
- มีคำอธิบายใต้การ์ด: ถ้าช่วงเปิดปั๊มสั้นกว่าประมาณ 6 วินาที แจ้งเตือนจะไม่หายเอง ต้องกดรับทราบ
- หลัง 503 หาย ฟอร์มเติมค่าจากบอร์ดใหม่
- poll ของการวัดที่ error ติดกัน 5 ครั้ง แสดงข้อความ "ติดต่อบอร์ดไม่ได้" และเปิดปุ่มให้ลองใหม่

**ไม่แก้ (Claude ตัดสิน):** `POST /api/protection` ไม่เช็ค `is_password_default` ผมตรวจแล้วว่า POST ของกฎแจ้งเตือนก็ไม่เช็ค จึงสอดคล้องกันอยู่แล้ว
ข้อเล็กที่เหลือเป็นเรื่องภายใน เช่น คอมเมนต์ ความเข้มของ regex ใน verify และช่องว่างของ test จะอยู่ในไฟล์งานค้างพร้อมเหตุผล
