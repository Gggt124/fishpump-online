ยังทำไม่ได้ตอนนี้

### จูน preset 3 ข้อที่ตั้งค่าไว้ชั่วคราว (ต้องมีค่าจริงจากเซนเซอร์)
- [ ] **"ปั๊มน้ำไม่ทำงานตามคำสั่ง"** ตอนนี้ < 0.3 A — วัดกระแสขณะปั๊มน้ำทำงานจริง

- [ ] เพิ่มกฎ "กระแสปั๊มสูงเกิน" หลังรู้กระแสพิกัดของปั๊ม (preset ยังไม่มีข้อนี้)
- [ ] pH ออกนอกช่วงจริง (จุ่มน้ำยาบัฟเฟอร์) → กฎ "pH ผิดช่วง" ขึ้น/หายตามเกณฑ์และช่วงกันสั่น
- [ ] รีเลย์ปั๊มน้ำค้าง: สั่งปิดรีเลย์ 1 แต่ปั๊มยังกินกระแส → กฎ "รีเลย์ปั๊มน้ำค้าง" ขึ้นแบบ latch (วิกฤต)

### ปั๊มและท่อจริง
- [ ] **ปั๊มจริง + flow switch จริงในท่อ:** ล่อน้ำแล้วใช้ปุ่ม "วัดให้" ได้ค่าสมเหตุสมผล ดึงท่อดูดขึ้นแล้วปั๊มถูกตัดตามเวลา (ระบบป้องกันเดินแห้งยังไม่เคยเห็นกับปั๊มจริง)
- [ ] **ขั้วของ flow switch:** NO ปิดวงจรเมื่อน้ำไหล (ถ้าใช้ NC ค่ากลับด้านและเฟิร์มแวร์ไม่มีตัวเลือกกลับขั้ว)
- [ ] **จูน preset ของระบบป้องกัน** (ผ่อนผัน `prime_sec`, `dry_trip_sec`, เวลารอลองใหม่) ด้วยเวลาล่อน้ำจริงของท่อคุณ ใช้ปุ่ม "วัดให้"
- [ ] **Backstop 130 วินาทีของโหมดทดสอบรีเลย์ 1** (`pump_control`) ทำงานเมื่อตัวควบคุมการวัดค้างจนรีเลย์เปิดเกิน 130 วินาที ขึ้น log `Relay-1 test exceeded 130000 ms cap, switching relay 1 off` กระตุ้นจากหน้าเว็บไม่ได้ (การวัดหยุดเองที่ 120 วินาที) จึง **สังเกตได้จาก log เท่านั้น** ถ้าเห็นบรรทัดนี้ตอนใช้งานจริง แปลว่าตัวควบคุมการวัดผิดปกติ ให้แจ้ง
- [ ] **การเดินต่อเมื่อ flow switch อ่านไม่ได้ตอนกด "วัดให้"** (เฟิร์มแวร์ตอบ 503 `flow_unavailable`) จำลองบนโต๊ะทดสอบยาก ตรวจด้วยโค้ดเท่านั้น

## (c) เลื่อนไว้ตามการตัดสินใจ

### Chiller protection
- [ ] ระบบป้องกัน Chiller (ทำนองเดียวกับป้องกันปั๊มเดินแห้ง) **ยังไม่ทำ** ตามที่ตัดสินใจเลื่อนไว้ ต้องมี spec ใหม่และต้องรู้พฤติกรรมจริงของ Chiller จากข้อ (b) ก่อน

### โปรเจกต์ MQTT / ThingsBoard — ต้องทำในโปรเจกต์นั้น
กฎอยู่ในเฟิร์มแวร์ ThingsBoard เก็บและแจ้งเตือน (ดูภาพรวมของแพลตฟอร์ม) สิ่งที่เฟิร์มแวร์เตรียมไว้แล้วคือ `uplink` ที่ไม่มีตัวส่ง รอ MQTT มาต่อ โปรเจกต์ MQTT **ต้อง**:

- [ ] **เพิ่ม SNTP** แล้วส่งฟังก์ชันเวลาจริงให้ `uplink_set_wall_clock()` (ฟังก์ชันคืนเวลา Unix เป็นมิลลิวินาที `wall_clock`) ถ้าไม่ทำ เหตุการณ์จะส่งโดยไม่มี `ts` หลังถือรอ 120 วินาที ThingsBoard จะประทับเวลาตอนรับเอง
- [ ] **ทำตามสัญญาของ `uplink_set_sink`** ใน `firmware/components/uplink/include/uplink.h`:
  - ห้ามเรียก `uplink_set_sink` จากใน MQTT event handler หรือจาก callback ของ sink เอง หรือจาก context ที่ถือ lock ที่ `send`/`is_connected` อาจใช้ (จะเกิด deadlock เพราะ `set_sink` รอ send ที่กำลังทำงานอยู่)
  - เรียก `set_sink` เฉพาะตอนตั้งค่าและตอนรื้อระบบ สถานะการเชื่อมต่อให้รายงานผ่าน `is_connected`
  - `send` ของ sink ต้อง **ไม่บล็อก** (เช่นใช้ `esp_mqtt_client_enqueue` ไม่ใช่การส่งที่รอ ack) เพราะ `uplink` ถือ lock ระหว่างส่ง และ task `uplink` รอ lock ตัวนี้
  - หลัง `set_sink` คืนค่า เฟิร์มแวร์รับประกันว่าจะไม่เรียก `ctx` เดิมอีก จึง free ได้
- [ ] **ทบทวนเพดานถือเหตุการณ์ 120 วินาที** (`UPLINK_CLOCK_HOLD_MAX_MS`) ว่าเหมาะกับ SNTP จริงไหม ตอนนี้: ถือเหตุการณ์ไว้ไม่เกิน 120 วินาทีหรือจนค้างใกล้เต็ม (24 จาก 32) แล้วส่งโดยไม่มี `ts` เวลาที่ตัวส่งหลุดนับรวมในเพดานด้วย (การถือไม่เริ่มใหม่เมื่อหลุดแล้วต่อใหม่) ต้องตัดสินว่ารับได้ไหมที่เหตุวิกฤตช้า 2 นาทีถ้า SNTP ไม่ติด
- [ ] ตรวจว่าเมื่อเชื่อมต่อใหม่ การส่ง attributes และ telemetry ไม่ชนกับการส่งเหตุการณ์ที่ถืออยู่ และตรวจด้วยตัวส่งจริงว่า preview ไม่ค้าง
- [ ] ตามแผนแพลตฟอร์ม: กฎอยู่ในเฟิร์มแวร์ ThingsBoard เก็บข้อมูลและส่งแจ้งเตือน และรองรับหลายลูกค้า/หลาย firmware (`identity` ใน preview มี `fw_type` และ `contract_version` ไว้สำหรับเรื่องนี้)

## (d) ข้อเล็กที่ตั้งใจไม่แก้ (minor ที่เลื่อนไว้) พร้อมเหตุผลบรรทัดเดียว

ไม่มีข้อไหนกระทบความปลอดภัยของปั๊มหรือทำให้ข้อมูลหาย เว้นแต่ที่ระบุ

### จากรอบเก็บงานก่อน MQTT (ledger ตามลำดับ task)

**Task 1 (กฎ PENDING / LED level)**
- ไม่มี test ว่าสถานะ FAULT เคลียร์ตัวนับ holding — เหตุผล: โค้ดเคลียร์ทุก verdict ที่ไม่ใช่ HOLD ตามเดิมและมี test ครอบคลุมทางอื่น
- ไม่มี test ตอนตัวจับเวลา hold วนรอบ (wrap) — เหตุผล: ใช้ลบแบบ unsigned เหมือนทุกที่ ผลต่างไม่เกินตัวเลขที่เล็กมาก
- การตรวจ verify เป็น substring อ่อน — เหตุผล: ตัวพฤติกรรมจริงมี test ใน QEMU ตรวจแล้ว

**Task 2 (blob v2)**
- test กรณี record เล็กลงแทบไม่ได้ตรวจอะไร — เหตุผล: spec ต้องการแค่ไม่อ่านเกินและกฎที่ได้ต้องผ่านการตรวจ ผู้ตัดสินให้คงไว้ (ต้นทุนถ้าผิด: test อ่อน)
- ตัวเลข `4` เป็น literal ใน test — เหตุผล: เป็นแค่ขนาด header ของ v1 ใน test เท่านั้น
- คอมเมนต์ header พูดว่า "bad length" — เหตุผล: คอมเมนต์ไม่ตรงนิดเดียว ไม่กระทบพฤติกรรม

**Task 3 (uplink)**
- `connected_cache` อัปเดตเฉพาะตอน `do_attributes` ทำงาน (ค้างค่าเก่าตอน hub ล่ม) — เหตุผล: เป็นข้อมูลแสดงผลใน preview เท่านั้น
- ตอนนาฬิกามาถึงขณะที่เหตุการณ์ถูกปล่อยไปแล้ว ไม่มี log บอกว่าโหมดไม่มี `ts` จบ — เหตุผล: log อย่างเดียว ไม่กระทบข้อมูล
- preview แสดง `waiting_for_clock:false` ตอนถือเหตุการณ์อยู่แต่ sink หลุด — เหตุผล: ตอนนี้ไม่มี sink จริง ค่อยตรวจกับ MQTT
- การตัดสินว่ามี `ts` หรือไม่ซ้ำกันสองที่ (ผลของ step กับ `unix_now`) — เหตุผล: ซ้ำเชิงโครงสร้าง ผลตรงกัน
- `pending_events` ถูกเขียนนอก `s.lock` — เหตุผล: เป็น uint32 ตัวเดียว ฝั่งอ่านใช้แสดงผล race ไม่เป็นอันตราย (โค้ดเดิม)

**Task 4 (LED)**
- แจ้งเตือนเตือน/ข้อมูลที่ยังไม่รับทราบ **บังสีเขียว "AP เปิด"** — เหตุผล: ตั้งใจตามลำดับใน spec และบันทึกไว้ใน `bench-test-pre-mqtt.md` ข้อ 7
- คอมเมนต์ของ `last_critical_seq` ควรเขียนว่า "ตั้งแต่บูตนี้" — เหตุผล: คอมเมนต์เท่านั้น
- LED ข้อมูลสีน้ำเงินค้างคล้ายสี recovery AP — เหตุผล: ต่างกันที่ค้าง/กระพริบ และ recovery AP ทับแจ้งเตือนเสมอ

**Task 5 (log/diag)**
- ไม่ตรวจค่าที่คืนจาก `esp_task_wdt_add(NULL)` ในทางที่ตั้งค่าแล้ว — เหตุผล: โค้ดเดิมก็ไม่ตรวจ ถ้าล้มจะไม่มี watchdog ของ task หลักแต่ไม่กระทบการทำงาน
- regex ของ verify (PT100 guard, เก็บ handle) เปราะ — เหตุผล: เป็นตัวตรวจเท่านั้น ถ้าโค้ดเปลี่ยนรูปจะเห็นเป็นผลไม่ผ่านให้แก้เอง
- handle ของ task ค้างถ้า init ซ้ำ — เหตุผล: ไม่มีทาง init ซ้ำในเฟิร์มแวร์นี้ ไม่มี task ถูกลบ

**Task 6 (dry-run guard)**
- guard ยังไม่ init ทำให้ได้ 409 "ต้อง stop ปั๊มก่อน" ซึ่งชวนเข้าใจผิด (INVALID_STATE) — เหตุผล: ของเดิม และเกิดเฉพาะ init ล้มซึ่งบอร์ดจะไม่ใช้งานอยู่แล้ว
- log กู้คืนหลัง retry อาจเอ่ยการกระทำที่ถูกแทนไปแล้ว — เหตุผล: log อย่างเดียว สถานะสุดท้ายถูกต้อง
- ตอบ `unavailable` แทน `measure_unavailable` ตาม spec §5 เมื่อ start ผิดพลาดแบบอื่น — เหตุผล (Ruling): ใช้รหัสเดียวกับ 503 อื่นและสาขานี้ตอนนี้เข้าไม่ถึง (ต้นทุนถ้าผิด: เปลี่ยนสตริงเดียว)

**Task 7 (UI การ์ดเดินแห้ง)**
- poll ตอนแท็บกลับมามองเห็นอาจซ้อนกับ poll ที่ค้างอยู่ (GET เกิน 1 ครั้ง) — เหตุผล: เป็นแค่คำขอ GET เพิ่ม 1 ครั้ง

**Task 8 (กระดิ่ง/overlay)**
- การปิด overlay หลังรับทราบใช้สรุปที่จับไว้ตอนกดปุ่ม — เหตุผล: คิดตามเหตุผลแล้วว่าถูกต้อง แต่ยังไม่ได้ทดสอบ และผลเสียถ้าผิดคือ overlay เด้งซ้ำหนึ่งรอบ
- overlay ไม่มี Tab trap (กด Tab ออกไปโฟกัสหน้าหลังได้) — เหตุผล: ไม่กระทบความปลอดภัย ปุ่มทั้งสองอยู่ในลำดับโฟกัสแรกและ overlay ปิดได้ด้วยเมาส์
- session หมดอายุโดยไม่เปลี่ยนหน้า overlay/เสียงจะค้างจนกว่าจะเปลี่ยนเส้นทางครั้งถัดไป — เหตุผล: เกิดเฉพาะ session หมดอายุตอนเปิด overlay ค้างไว้ และหายเองเมื่อ route เปลี่ยน
- `<dialog>` ของ confirm อยู่ top layer จึงเรียงทับ overlay — เหตุผล: ได้ผลที่ต้องการ (กล่องยืนยันรับทราบต้องมองเห็นเหนือ overlay) ไม่ใช่ข้อบกพร่อง

**ค้างจากการตรวจรอบแก้สุดท้าย (ควรแก้เป็นอย่างแรกเมื่อกลับมา เพราะเกี่ยวกับการเปิดปั๊มกลับ)**
- กล่องยืนยันตอนกด "รับทราบทั้งหมด" บน overlay วางเคอร์เซอร์ที่ปุ่ม "ยืนยัน" และไม่กันการกดซ้ำ ถ้าตั้งใจกดปุ่มรับทราบแล้วกด Enter ค้างหรือดับเบิลคลิกเร็ว อาจยืนยันโดยไม่ทันอ่านคำเตือน — เหตุผลที่ยังไม่แก้: ต้องเล็งกดปุ่มรับทราบเองก่อน (การกดปุ่มเดียวโดยไม่ตั้งใจถูกปิดไปแล้ว) และกระบวนการไม่มีรอบแก้ที่สอง; วิธีแก้: ใส่ flag กันกดซ้ำ และโฟกัส "ยกเลิก" ในกล่องนี้ (~6 บรรทัด)
- คำเตือน "ปั๊มน้ำอาจเริ่มทำงานอีกครั้ง" ตัดสินตอนเปิดกล่องยืนยัน ถ้าเดินแห้งตัดในไม่กี่วินาทีที่กล่องเปิดอยู่ จะรับทราบไปโดยไม่มีคำเตือน — เหตุผลที่ยังไม่แก้: ช่วงเวลาไม่กี่วินาที และถ้ายังไม่มีน้ำ ระบบจะตัดซ้ำเอง; วิธีแก้: ตรวจซ้ำตอนกดยืนยัน หรือแสดงคำเตือนทุกครั้งที่มีเหตุวิกฤต
- ถ้าเหตุถูกรับทราบจากเครื่องอื่นระหว่างดึงสถานะ กล่องยืนยันอาจเปิดโดยไม่มี overlay ข้างหลัง — เหตุผล: กดยืนยันก็แค่รับทราบสิ่งที่เหลือ ไม่มีผลเสีย

**ข้อสังเกตเพิ่มเติม (ไม่ใช่ข้อใน ledger)**
- คอมเมนต์ใน `web_server.c` ยังเขียน "poll every 10 s" — เหตุผล: คอมเมนต์ไม่กระทบพฤติกรรม
- กระดิ่งตำแหน่งคงที่มุมขวาบนอาจใกล้ปุ่มสลับธีมบนมือถือ — เหตุผล: ต้องดูตอน bench (`bench-test-pre-mqtt.md` ข้อ 5.3)
- เสียง โฟกัส และเลย์เอาต์ ยังไม่ได้ลองบนเบราว์เซอร์จริงกับบอร์ด — เหตุผล: ไม่มีบอร์ด ต้องดูตอน bench (controller ลองด้วย mock API ในเบราว์เซอร์แล้ว)

**แก้แล้วในรอบแก้สุดท้าย (ไม่ต้องทำอีก):** Task 2 คอมเมนต์ layout v1; Task 6 verify เกือบ tautology; Task 7 poll วัดล้มเหลว 5 ครั้งแล้วบอร์ดอาจยังวัดอยู่ (ตอนนี้ sync ใหม่เมื่อ poll สถานะถัดไปสำเร็จ); เสียงบี๊ปค้างในแท็บที่ซ่อน

### จากระบบป้องกันปั๊มเดินแห้ง (`2026-11-16-pump-dry-run-protection-results.md` ส่วน 4 และ 7) ที่ Task 6–7 ไม่ได้แก้

(ข้อที่แก้แล้วในรอบนี้: การซ่อม raise/clear ของแจ้งเตือน, การอ่าน flow switch ไม่ได้ตอนวัด, ช่วงตัวเลขในการ์ด, ข้อความอธิบายเมื่อช่วงเปิดสั้น, poll ตอนซ่อนแท็บ, ฟอร์มไม่เติมค่าหลัง 503, poll วัดล้มเหลว, ข้อ "4." ซ้ำ, ขั้น bench stop ระหว่าง WAIT)

- Task 1: test ค่าขอบบางตัว, `NULL cfg` ไม่ถูกตรวจ, เทียบ uint64 กับค่าคงที่ int — เหตุผล: เรียกจากภายในด้วยค่าที่ผ่านการตรวจแล้วเสมอ
- Task 2: ลด `dry_trip_sec` ต่ำกว่า accum ที่ค้างจะ trip ใน tick ถัดไป; ค่า ack = accum บางส่วน; `dt` ไม่มีขอบบนถ้า scheduler ค้าง; ช่องว่างของ test (ack ใน DISABLED, สายขาดกลางคัน, ลด `max_retries` ระหว่าง WAIT) — เหตุผล: เป็นพฤติกรรมที่ปลอดภัย (ตัดเร็วขึ้น ไม่ใช่ช้าลง) และเกิดเฉพาะแก้ค่าระหว่างทำงาน
- Task 3: verify ไม่พิสูจน์ว่าไม่มี callback ก่อน Give; `on_ack` เป็น NULL ได้ `acked:1`; คอมเมนต์เก่า `alarm_presets.c:18-19`; engine ไม่มี runtime test — เหตุผล: ตัวตรวจ/คอมเมนต์ และ engine ต้องมี FreeRTOS+NVS จึงทดสอบบน QEMU ไม่ได้
- Task 4: regex verify ผ่านด้วยคอมเมนต์; เงื่อนไข inhibit เขียนซ้ำ 3 ที่; `on_phase` ซ้ำกับ `start_phase`; header ไม่อธิบายกรณี `resume=false && running`; คอมเมนต์ `:429`; ไม่มี log ตอน inhibit; `active_set` หยุดเปลี่ยนตอน inhibited; `water_test(false)` ถูกปฏิเสธเมื่อ faulted; ไม่มี runtime test ของ `pump_control`; `notify_state_changed` ถูกเรียกใต้ mutex — เหตุผล: ทั้งหมดไม่กระทบพฤติกรรม และ "ห้ามเปลี่ยนพฤติกรรมปั๊มในรอบนี้"
- Task 5: อ่านสถานะล้มแล้วป้อน `relay_on=false` (เริ่มหน้าต่างผ่อนผันใหม่); flow_switch ยังไม่ init → ตัดเสมอ (fail-safe); flag resume ลดระดับเมื่ออ่านสถานะตอน ack ล้ม; โหลด NVS สองครั้งตอนบูต; `portMAX_DELAY` บน `s_apply` ใน HTTP path; `pending_off` ล้างผ่านสถานะสำรอง; init พลาดหลัง register ไม่มีทางออก (อยู่ฝั่งปลอดภัย); `t0` นับหลัง `water_test` คืนค่า; `ESP_LOGE` ใน `persist_failed`; persist ตอนล็อกพลาดไม่ถูกลองใหม่; verify อิงชื่อ — เหตุผล: ทั้งหมดเป็นกรณีขอบหรือเกิดเฉพาะความล้มเหลวของระบบที่ fail-safe อยู่แล้ว และการแก้แตะเส้นทางควบคุมปั๊ม
- Task 6: start ตอนปั๊มทำงานอยู่และ inhibited ได้ 409 แทน `already_running` (ตั้งใจ); verify ไม่ตรวจว่า stop ไม่ถูกบล็อก — เหตุผล: การเปลี่ยน API ที่ตั้งใจ / ตัวตรวจ
- Task 7: รายการฟังก์ชันใน `test_ui` ไม่ครบและไม่เช็กข้อความไทย; การจัดการ class `is-warn`; GET resume มาช้าหลังออกจาก dashboard อาจ poll หน้าที่ซ่อน 1 ครั้ง; GET resume ล้มทำให้ปุ่มวัดเปิดใช้อีกทั้งที่อาจยังวัดอยู่ — เหตุผล: เกิดยากและผลเสียแค่ข้อความ "กำลังวัดอยู่"
- Task 8: regex ตรวจลำดับ lock ยังอ่อน; ไม่มีคอมเมนต์ว่าการตรวจบนสำเนาพึ่ง `write_lock` — เหตุผล: ตัวตรวจ/คอมเมนต์
- final review: guard กับ alarm engine สถานะไม่ตรงกันเพราะหน่วยความจำไม่พอ ไม่มีการซ่อมเอง — เหตุผล: Task 6 ซ่อมกรณี raise/clear ถูกปฏิเสธแล้ว (ลองซ้ำทุก tick) ที่เหลือคือกรณีที่ engine ล้มถาวรซึ่งหายากมาก
- final review: สถานะ guard/pump ไม่ทันกันตอนจบ WAIT ทำให้ start ล้มแล้วเรียก `stop_water` — เหตุผล: หายาก และผลคือปั๊มหยุดอยู่ (ฝั่งปลอดภัย)
